# B5-3 동료평가 대비 완벽 가이드

> 문과 중졸도 이해할 수 있게, 하나도 빠짐없이 정리.

---

## 1. 이 과제가 뭔가요? (한 줄로)

**로그인이 되고 회원끼리 연결되는 웹 서비스를 FastAPI로 만드는 과제.**

### 쉽게 설명하면

인터넷에서 회원가입/로그인이 되는 사이트를 만들어본 적이 없다면, 이 과제가 그 첫 경험입니다:

- **회원가입/로그인/로그아웃**: 사용자를 식별하는 기능 (인증)
- **접근 제어**: 로그인한 사람만 글을 쓰고/수정하고/삭제할 수 있게 (인가)
- **회원 간 연결**: 사용자가 다른 사용자를 팔로우(follow)하여 회원 간 관계를 맺는 기능
- **상태 변경**: 글이 초안 → 공개 → 비공개로 바뀌는 것 (상태 전이)

### 왜 이걸 배우나요?

거의 모든 웹 서비스에 "로그인"이 있습니다. 쇼핑몰, SNS, 은행 — 전부 "누가 쓰는지" 알아야 합니다. 이 과제는 **인증(로그인)과 인가(권한 제어)의 원리**를 직접 구현하면서 배우는 것이 목표입니다.

## 3. 작업 진행 순서

### Step 1: 프로젝트 구조 설계
- FastAPI + SQLAlchemy + Jinja2 + SQLite
- 계층 분리: routers/ → services/ → repositories/ → models/

### Step 2: 데이터베이스 모델 설계
- User (사용자): id, username, email, hashed_password
- Board (게시판): id, name, description
- Post (게시글): id, title, content, status, user_id(FK), board_id(FK)
- 연관관계: User 1:N Post, Board 1:N Post, User N:M User (팔로우, Follow 조인 테이블)

### Step 3: 인증 시스템 구현
- 회원가입: 비밀번호를 bcrypt로 해싱해서 저장
- 로그인: 비밀번호 검증 → 세션 쿠키 발급 (itsdangerous 서명)
- 로그아웃: 세션 쿠키 삭제
- 세션 확인: 모든 요청에서 쿠키 검증

### Step 4: 접근 제어 (인가)
- 공개 경로: 홈, 게시판 목록, 게시글 읽기
- 보호 경로: 글 쓰기, 수정, 삭제, 공개/비공개 전환
- 미로그인 시 로그인 페이지로 리다이렉트

### Step 5: 상태 전이 로직
- draft(초안) → published(공개): "공개" 버튼
- published(공개) → hidden(비공개): "비공개" 버튼
- hidden(비공개) → published(공개): 다시 "공개" 버튼
- 각 전이는 서비스 계층에서 검증

### Step 6: UI 구현 (Jinja2 템플릿)
- 로그인 전: "로그인" 버튼만 보임
- 로그인 후: "OOO님 환영합니다" + "글쓰기" + "로그아웃" 버튼
- 게시글 목록/상세/작성/수정 화면

### Step 7: 문서화
- README (37KB): 실행 방법, 테스트 계정, 경로 정책, 아키텍처
- GITFLOW.md: Git 협업 워크플로우
- IMPLEMENTATION_REPORT.md: 구현 보고서

## 4. 진행 중 생긴 문제와 해결

### 문제 1: 세션 관리 방식 선택
- **상황**: 로그인 상태를 유지하려면 세션 또는 JWT 중 선택 필요
- **해결**: 세션 기반 인증 선택 (itsdangerous로 서명된 쿠키)
- **판단 기준**: 
  - 세션: 서버가 상태를 기억, 구현 단순, 단일 서버에 적합
  - JWT: 상태 없음, 확장성 좋음, 하지만 구현 복잡
- **선정 이유**: 학습 목적이므로 단순한 세션 방식이 적합. JWT는 보너스로 별도 구현

### 문제 2: 비밀번호 저장 방식
- **상황**: 비밀번호를 그대로 DB에 저장하면 보안 사고
- **해결**: bcrypt로 해싱해서 저장 (passlib)
- **판단 기준**: "비밀번호를 원문으로 복구할 수 있어야 하는가?" → 아니요, 해싱은 단방향

### 문제 3: 권한 검사 중복
- **상황**: 매 라우터마다 "로그인 했는지" 확인 코드가 중복
- **해결**: FastAPI 의존성 주입(Depends)으로 공통 권한 검사 함수 구현
- **판단 기준**: "같은 코드가 반복되는가?" → 네, Depends로 해결

### 문제 4: 상태 전이 시 유효하지 않은 경로
- **상황**: draft → hidden으로 직접 가면 안 됨 (초안을 바로 비공개로 할 수 없음)
- **해결**: 서비스 계층에서 상태 전이 규칙 검증
- **판단 기준**: "모든 상태 변경이 허용되어야 하는가?" → 아니요, 비즈니스 규칙에 따라 제한

## 5. 선택의 기로 — 비교 및 선정 이유

### 선택 1: 인증 방식

| 옵션 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **세션** (선택) | 서버가 쿠키로 로그인 상태 기억 | 단순, 단일 서버에 적합 | 서버 재시작 시 세션 초기화 |
| JWT | 토큰으로 상태 없이 인증 | 확장성, 분산 서버 | 구현 복잡, 토큰 만료 관리 |

**선정 이유**: 학습 목적, 단일 서버, 구현 단순성. JWT는 보너스로 별도 구현.

**감내**: 서버를 재시작하면 세션이 초기화됨 (다시 로그인해야 함). 하지만 학습 환경에서는 감내 가능.

### 선택 2: 데이터베이스

| 옵션 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **SQLite** (선택) | 파일 기반 | 설치 불필요, 가벼움 | 동시 쓰기 제한 |
| PostgreSQL | 서버 기반 | 동시성, 확장성 | 설치/설정 필요 |

**선정 이유**: 개발 환경에서 빠르게 실행. 과제에서 "SQLite(개발), PostgreSQL(운영 권장)"으로 명시.

**감내**: 여러 사용자가 동시에 쓰면 성능 저하. 하지만 학습 목적이므로 감내.

### 선택 3: 계층 분리

| 옵션 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **4계층** (선택) | Router → Service → Repository → Model | 관심사 분리, 테스트 용이 | 파일 수 많음 |
| 2계층 | Router → Model | 단순 | 비즈니스 로직이 Router에 섞임 |

**선정 이유**: 과제에서 "라우터, 서비스, 저장소, 모델 코드는 역할에 맞게 분리"를 명시적으로 요구.

**감내**: 파일이 많아서 구조 파악에 시간이 걸림. 하지만 유지보수성이 훨씬 좋음.

### 선택 4: 비밀번호 해싱 알고리즘

| 옵션 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **bcrypt** (선택) | 의도적으로 느린 해싱 | 무차별 대입 공격에 강함 | 해싱 시간이 김 |
| SHA-256 | 빠른 해싱 | 속도 빠름 | 무차별 대입에 취약 |

**선정 이유**: 비밀번호는 "느린 해싱"이 안전. 빠르면 해커가 빠르게 대입 가능.

**감내**: 로그인 시 약간의 지연. 하지만 보안이 훨씬 중요.

## 7. 평가 시 예상 질문과 답변

### Q1. "인증과 인가의 차이가 뭔가요?"
**답**: 
- **인증(Authentication)**: "누구인가?" — 로그인해서 사용자를 식별하는 것
- **인가(Authorization)**: "무엇을 할 수 있는가?" — 로그인한 사용자만 글을 쓸 수 있게 권한을 제어하는 것

예: 로그인 = 인증, "로그인한 사람만 글 쓰기 가능" = 인가

### Q2. "세션 기반 인증이 어떻게 작동하나요?"
**답**: 
1. 사용자가 아이디/비밀번호 입력
2. 서버가 비밀번호를 bcrypt로 검증
3. 맞으면 서버가 서명된 쿠키(itsdangerous)를 발급
4. 이후 모든 요청에 쿠키가 자동으로 전송
5. 서버가 쿠키를 검증해서 "이 사람은 OOO"라고 식별

### Q3. "비밀번호를 어떻게 저장했나요?"
**답**: bcrypt로 해싱해서 저장합니다. 비밀번호 "test1234"를 저장할 때 "test1234" 자체가 아니라, "$2b$12$N9..." 같은 해시값을 저장합니다. 해시는 단방향이라 원문을 복구할 수 없습니다. 로그인 시에는 입력값을 같은 방식으로 해싱해서 저장된 해시와 비교합니다.

### Q4. "왜 bcrypt를 썼나요? SHA-256은 안 되나요?"
**답**: SHA-256은 너무 빨라서 해커가 초당 수십억 번 대입할 수 있습니다. bcrypt는 의도적으로 느리게 설계되어서 무차별 대입 공격에 강합니다. 비밀번호 저장에는 "느린 해싱"이 안전합니다.

### Q5. "연관관계를 어떻게 설정했나요?"
**답**: SQLAlchemy의 relationship과 ForeignKey를 사용했습니다:
- User 1:N Post: 한 사용자가 여러 글을 쓸 수 있음
- Board 1:N Post: 한 게시판에 여러 글이 있을 수 있음
- Post.user_id → User.id (FK)
- Post.board_id → Board.id (FK)
- User N:M User (팔로우): Follow 조인 테이블로 회원 간 연결 관계 모델링
  - Follow.follower_id → User.id (팔로우 하는 사람)
  - Follow.followed_id → User.id (팔로우 당하는 사람)
  - UniqueConstraint로 중복 팔로우 방지

### Q6. "상태 전이 로직을 설명해주세요"
**답**: 게시글은 3가지 상태를 가집니다:
- **draft(초안)**: 작성 중, 아직 공개 안 됨
- **published(공개)**: 누구나 볼 수 있음
- **hidden(비공개)**: 작성자만 볼 수 있음

전이 규칙:
- draft → published (공개)
- published → hidden (비공개)
- hidden → published (다시 공개)

이 규칙은 서비스 계층에서 검증해서 잘못된 전이를 막습니다.

### Q7. "계층을 왜 4개로 나눴나요?"
**답**: 각 계층이 하나의 역할만 담당하도록:
- **Router**: URL 처리, 요청/응답 (사용자 접점)
- **Service**: 비즈니스 로직, 상태 전이 검증 (규칙)
- **Repository**: 데이터베이스 CRUD (저장)
- **Model**: 데이터 구조 정의 (형태)

이렇게 나누면 비즈니스 로직을 수정할 때 Service만 보면 되고, DB 쿼리를 수정할 때 Repository만 보면 됩니다.

### Q8. "로그인하지 않은 사용자가 글을 쓰려고 하면 어떻게 되나요?"
**답**: 보호 경로에 접근하면 로그인 페이지로 리다이렉트됩니다. FastAPI의 Depends를 사용해서 "현재 사용자"를 확인하고, 없으면 로그인 페이지로 보냅니다.

### Q9. "환경변수는 어떻게 관리했나요?"
**답**: .env 파일에 민감 정보(비밀키, DB 경로 등)를 저장하고, .gitignore에 .env를 포함시켜서 GitHub에 푸시되지 않습니다. .env.example에 키 목록만 적어서 다른 사람이 어떤 변수가 필요한지 알 수 있습니다.

### Q10. "UI에서 로그인 전/후가 어떻게 달라지나요?"
**답**: 
- **로그인 전**: "로그인" 버튼만 보임, "글쓰기" 메뉴 안 보임
- **로그인 후**: "OOO님 환영합니다" + "글쓰기" + "내 글" + "로그아웃" 버튼 표시

Jinja2 템플릿에서 `current_user` 변수로 분기해서 다른 UI를 보여줍니다.

### Q11. "회원 간 팔로우 기능을 어떻게 구현했나요?"
**답**: Follow 조인 테이블(follows)을 만들어 회원 간 N:M 관계를 모델링했습니다:
- **Follow 모델**: follower_id(팔로우 하는 사람), followed_id(팔로우 당하는 사람)
- **API**: POST /api/users/{id}/follow (팔로우), DELETE /api/users/{id}/follow (언팔로우)
- **화면**: /users/{id} 프로필에서 팔로우/언팔로우 버튼, /users/{id}/following(팔로잉 목록), /users/{id}/followers(팔로워 목록)
- **비즈니스 규칙**: 자기 자신 팔로우 금지, 중복 팔로우 방지 (UniqueConstraint)
- **계층 분리**: FollowRouter → FollowService(규칙 검증) → FollowRepository(DB CRUD)

### Q12. "팔로우 관계를 데이터베이스로 어떻게 모델링했나요?"
**답**: follows 테이블에 두 개의 외래키(follower_id, followed_id)를 두어 User-User 간 N:M 관계를 표현했습니다. SQLAlchemy의 relationship으로 User.following_assoc(내가 팔로우하는 목록)과 User.followers_assoc(나를 팔로우하는 목록) 양방향 접근을 제공합니다. 순환참조 방지를 위해 응답에서는 ID만 사용합니다.
